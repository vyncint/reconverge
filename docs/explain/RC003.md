# RC003 — `&mut [T]` as a kernel parameter

A kernel takes `&mut [T]`. On the GPU that one exclusive reference is
handed to *every thread of the launch at once*.

## A minimal failing kernel

```rust
#[kernel]
pub fn scale(data: &mut [f32]) { // RC003
    if let Some(x) = data.get_mut(0) {
        *x *= 2.0;
    }
}
```

## What happens on hardware

`&mut T` means *exclusive* access in Rust — the whole point of the type.
But a kernel body runs once per thread: launch this on 4096 threads and
there are 4096 live `&mut [f32]` to the same memory, each believing it is
alone. Any two threads writing the same element is a data race, which is
undefined behavior; there is no lock, no fence, and no diagnostic. Typical
symptoms are lost writes and values that differ run to run — and a build
that looks perfectly safe, because the race is created by the launch, not
by any line the borrow checker can see.

## The fix

Use `DisjointSlice<T>`: each thread can obtain a mutable reference only to
the element(s) its own proof-carrying index selects, so exclusivity is real
per thread:

```rust
#[kernel]
pub fn scale(mut data: DisjointSlice<f32>) {
    let i = thread::index_1d();
    if let Some(x) = data.get_mut(i) {
        *x *= 2.0;
    }
}
```

Read-only sharing is fine as `&[T]` — shared references are not a
parallel-write hazard and are not flagged.

## Notes

- Reported at `deny` confidence: the parameter type alone proves the
  hazard; no divergence analysis is involved.
- This is the enforcement gap cuda-oxide's own safety table documents for
  `&mut [T]` parameters; `DisjointSlice` is upstream's intended tool.
- SIMT fundamentals: `cargo reconverge learn` ships four interactive
  lessons (divergence, barriers, masks, reconvergence), fully offline.
